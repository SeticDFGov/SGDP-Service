# CLAUDE.md — SGDP-Service (API .NET 8)

API do SGDP ("API-SUBGD"), sistema em **produção** da SUBGD/GDF. .NET 8 + ASP.NET Core Web API + EF Core 8 (Npgsql/PostgreSQL) + Keycloak. O módulo PGIA (Decreto nº 48.901/2026) é implementado aqui de forma **aditiva e isolada**. Especificações na pasta pai: `analise_integracao_pgia_sgdp.md` (manda em caso de dúvida), `schema_pgia_48901.sql`, `formulario_decreto_48901.md`, `mock_formulario_pgia.html`.

## Regras invioláveis (sistema em produção)

1. **Nunca criar perfis novos nem roles novas no Keycloak.** `GetOrCreateUserAsync` (`app/Repositorio/AuthRepositorio.cs`) sobrescreve `Users.Perfil` com a **primeira** role do token a cada login — role nova no Keycloak pode trocar silenciosamente o perfil de usuários existentes. Papéis do PGIA vivem na coluna nullable `Users.PapelPgia`, administrada por endpoint do próprio sistema. **Não modificar** `GetOrCreateUserAsync`, `app/Auth/Perfis.cs` nem `app/service/PermissionService.cs`.
2. **Nenhuma alteração em tabela existente**, exceto a coluna nullable `PapelPgia` em `Users` (fase 0). Todas as tabelas novas com prefixo `pgia_`. **Nunca editar migrations antigas.** Uma migration nova por fase. Antes de fechar a fase: `dotnet ef migrations script <anterior> <nova>` e conferir que o SQL só cria objetos `pgia_*` (mais o `ALTER TABLE "Users" ADD "PapelPgia"` na fase 0). **O CI (`.github/workflows/apply-migrations.yml`) aplica migrations automaticamente no merge para a main** — já houve migration que quebrou o banco (`app/MIGRATION_INSTRUCTIONS.md`).
3. **Não alterar contrato de endpoint existente.** Exceção permitida: campo `PapelPgia` a mais na resposta do `GET /api/Auth/me` (campo extra não quebra o front).
4. Autorização do PGIA em serviço próprio: `PgiaPermissionService` (papel + ação + recurso + filtro de dados por órgão), espelhando o desenho do `PermissionService` sem tocá-lo. Perfil `admin` do SGDP tem acesso total ao PGIA. **Todo endpoint PGIA valida permissão no backend**; checagem do front é só usabilidade.
5. Endpoints públicos **somente na fase 5**, em controller próprio com `[AllowAnonymous]` explícito, devolvendo apenas os campos do art. 24 (nunca dados pessoais); solicitações do cidadão com validação de entrada e protocolo gerado no servidor.
6. **Não tocar nos testes legados** (`test/` referencia classes que não existem mais — `Projetos`, `CategoriaRepositorio` etc.; o projeto `test/` **não compila**, problema conhecido, fora de escopo). Testes novos do PGIA vivem no projeto separado `test-pgia/` (rodar com `dotnet test test-pgia/test-pgia.csproj`).
7. **Sem dependências novas** salvo estritamente necessário e justificado. QuestPDF já existe para PDFs. **Exceção aprovada (plano da Governança Estratégica, decisão 39): `DocumentFormat.OpenXml` 3.5.1 (licença MIT, o SDK oficial do Open XML mantido pela Microsoft/.NET Foundation), desde a E3, só para gerar o XLSX das planilhas do módulo** (cabeçalho fixo, filtro, números e datas com formato, listas com validação de dados e várias abas, o que um CSV não faz; nada no BCL gera XLSX).

## Isolamento entre módulos e gestão de acessos (rodada de 2026-09-21)

Pedido do usuário: quem entra só pelo login do Keycloak, sem acesso algum, não enxerga nada — nem na tela nem na API — e cada perfil vê apenas os módulos que tem. **Vale para todo controller novo.**

- **Módulos** (`app/Auth/ModulosSgdp.cs`): `demandas` (painel, demandas, entregáveis e os cadastros de apoio Demandante/Esteira/Área executora), `pgia`, `contratacoes` (Supervisão Contínua), `planejamento` (Governança Estratégica, desde 2026-09-24; seção própria no fim deste arquivo), `administracao` (só a role admin).
- **Acesso efetivo = Keycloak + sistema** (decisão do usuário: somar, para ninguém perder acesso no deploy). Regra única: `AcessoModuloService.CalcularModulos`.
  - Keycloak: `admin` abre tudo, `gestor` abre Demandas e a role `pgia` do grupo abre o PGIA como agente do art. 13.
  - Sistema: linhas de `acesso_modulo` com origem `sistema` (Demandas, PGIA e Governança Estratégica) e os papéis de módulo que já existiam. `PapelPgia` válido dá acesso ao PGIA; `PapelContratacoes = ctr_analise` é o acesso à Supervisão Contínua (não há linha de concessão para ele). Na Governança Estratégica o acesso é só a concessão: o papel do módulo (`pe_papel_usuario`) é gravado junto com ela, mas o cálculo do acesso não o lê (regra do deploy).
  - Sem nenhuma fonte, a lista é vazia.
- **Enforcement**: `ModuloAcessoClaimsTransformation` (uma consulta por requisição autenticada; anônima passa direto) põe uma claim `sgdp_modulo` por módulo numa identidade à parte. `ModulosSgdp.AdicionarPoliticas` cria as políticas `modulo:*` (`RequireClaim`).
  - Controllers com a política do módulo: Demanda, Dashboard, Entregáveis, Demandante, Área executora e Esteira → `modulo:demandas`; os 6 controllers PGIA autenticados → `modulo:pgia` (substituiu `Roles = "admin,pgia"`); Processo, Manifestação e Importação de contratações → `modulo:contratacoes`; `PePessoasController`, `PeModeloController`, `PeOrgaosController`, `PeRegistrosController`, `PePeticController`, `PeDeliberacoesController`, `PeArquivosController`, `PePdticController`, `PeDocumentoController`, `PeFluxosController` e `PeAcompanhamentoController` → `modulo:planejamento`.
  - Continuam `Roles = "admin"`: `PgiaAdminController`, `CtrAdminController` e o novo `AcessoController`.
  - Exceções declaradas: `AuthController` (o `/me` precisa responder a quem não tem acesso), `PedidoAcessoController` (pedir acesso é justamente para quem não tem módulo algum), `AuthLocalController` e `PgiaPublicoController`.
  - **`AcessoModuloTest.TodoControllerExigeOModuloOuOAdmin` falha se aparecer controller sem essa decisão.**
- **Ordem das roles** (`ModulosSgdp.RolesComPerfilPrimeiro`, usado no `OnTokenValidated`): o perfil entra primeiro (admin > gestor > basico, e `basico` sempre existe como fallback), depois as demais roles do token. Motivo: os controllers leem o perfil com `FindFirst(ClaimTypes.Role)`, e um gestor que também tinha a role `pgia` chegava como perfil "pgia" e perdia a edição de demandas. Isso substituiu o "empresta basico só para quem tem pgia".
- **Tabela `acesso_modulo`** (migration **`20260921163934_AcessoModulos`**, script revisado: só `CREATE TABLE acesso_modulo` + PK + 2 CHECKs + FK cascade para `Users` + índice único `(user_id, modulo, origem)`; nenhuma tabela existente alterada). Mapeamento em `Models/Acesso/AcessoModelConfiguration.cs`.
  - Origem `sistema`: concessão da tela (com `concedido_em/por`, é a trilha de auditoria da concessão).
  - Origem `keycloak`: **retrato** das roles no último login, gravado no `/me` (`SincronizarRetratoKeycloakAsync`, só escreve quando muda; corrida de dois logins é absorvida). Serve **só para exibição** — a autorização lê sempre as roles do token da requisição (há teste).
- **`GET /api/Auth/me`** ganhou `Modulos` (lista efetiva; recalculada depois do `GetOrCreateUserAsync`, porque no primeiro login a transformação ainda não acha o usuário). `AcessoPgia` passou a ser o acesso efetivo ao módulo PGIA. `Perfil` sai pela ordem acima.
- **API de gestão** (`AcessoController`, `api/acessos`, admin):
  - `GET usuarios?Filtro=&Modulo=&Page=&PageSize=`: paginada. `Modulo` aceita um módulo ou `nenhum`; valor fora do domínio devolve lista vazia; o filtro usa o retrato para as roles.
  - `GET usuario/{id}`.
  - `PUT usuario/{id}` com `{ Demandas, Pgia, PapelPgia, Contratacoes }`: grava concessões e papéis de uma vez. Tirar o PGIA tira o papel; papel sem o módulo volta 400.
  - Erros saem como **400/404 com `{Code, Message}`** (faixa **9xx**: `AcessoUsuarioNaoEncontrado = 900`, `AcessoInvalido = 901`), não como o 500 herdado.
- **SGDI libera o agente do art. 13**: `PUT api/pgia/governanca/pessoa/{userId}/acesso-modulo` `{ Ativo }` (gate `CanEdit(PessoaVinculo)`). `PgiaPessoaAcesso` ganhou `AcessoModulo` (concessão) e `AcessoModuloKeycloak` (retrato de `pgia` ou de admin), preenchidos em lote pelo controller. O `PgiaGovernancaController` recebe `IAcessoModuloService`.
- **Modo local**: `LoginLocalRequest.ConcederModulos` (`demandas`/`pgia`/`planejamento`) grava concessões de teste (`concedido_por = "modo-local"`); a da Governança Estratégica anda com `PapelPlanejamento` (ver a seção do módulo).
- **Limitação**: uma pessoa com acesso vindo do Keycloak não perde esse acesso pela tela — isso é gerido no Keycloak. A tela mostra a origem.

## Pedidos de acesso (rodada de 2026-09-21, segundo pedido)

Pedido do usuário: o botão "Pedir acesso" do card registra um pedido (módulo + justificativa opcional); a administração aprova, já escolhendo o papel no PGIA e liberando na hora, ou recusa com motivo, que a pessoa lê no card; a SGDI também decide os pedidos do PGIA. Front: seção de mesmo nome no `CLAUDE.md` do SGDP-Angular.

- **Tabela `pedido_acesso`** (migration **`20260921174607_PedidosAcesso`**, script revisado: só `CREATE TABLE pedido_acesso` + PK + 2 CHECKs (módulo em `ModulosSgdp.Liberaveis`, situação em `SituacaoPedidoAcesso.Todas`) + FK cascade para `Users` + `ux_pedido_acesso_pendente` (único `(user_id, modulo) WHERE situacao = 'pendente'`) + `ix_pedido_acesso_situacao (situacao, criado_em)`; nenhuma tabela existente alterada). Colunas: `justificativa` e `motivo_recusa` varchar(500), `criado_em`, `decidido_em`, `decidido_por` (e-mail; **nulo num aprovado = encerrado sozinho**, o acesso chegou por outro caminho), `papel_pgia` (papel dado na aprovação, histórico). Mapeamento em `AcessoModelConfiguration`. **`situacao` é token de concorrência** (`IsConcurrencyToken`).
- **`ModulosSgdp.Liberaveis`** = Demandas, PGIA, Supervisão Contínua e Governança Estratégica (o que o sistema libera; a Administração só vem do Keycloak). `SituacaoPedidoAcesso` (pendente/aprovado/recusado) mora em `ModulosSgdp.cs`, ao lado de `OrigemAcesso`.
- **Quem decide** (`DecisorPedidos`, em `IPedidoAcessoService.cs`): perfil admin decide todos os liberáveis; `PapelPgia = pgia_sgdi` decide o PGIA; `pe_admin` decide a Governança Estratégica (desde 2026-09-24; quem tem os dois papéis decide os dois); o resto não decide nada. O `DecisorAsync` só consulta `pe_papel_usuario` para quem tem a claim do módulo `planejamento` e não é admin.
- **API** (`PedidoAcessoController`, `api/pedidos-acesso`, só `[Authorize]`):
  - `POST` `{ Modulo, Justificativa }`: pede. Módulo que a pessoa já tem, Administração (mensagem explica que vem do Keycloak) ou fora do domínio → 400. Pendente do mesmo módulo → devolve o mesmo (a corrida de dois cliques cai no índice único e também devolve o que ficou).
  - `GET meus`: o último pedido de cada módulo (o card mostra aguardando ou recusado com motivo; `MotivoRecusa` só sai na recusa).
  - `GET ?Situacao=&Modulo=&Filtro=&Page=&PageSize=`: a fila de quem decide (403 para quem não decide). Pendentes primeiro, por ordem de chegada (Id); depois os decididos, do mais novo. Situação ou módulo fora do domínio/escopo → lista vazia. Parâmetro da action chama `consulta` (armadilha do binding).
  - `GET pendentes?modulo=`: `{ Total }` do escopo de quem consulta; **zero para quem não decide** (sem 403, para o contador nunca acionar o interceptor do front).
  - `POST {id}/aprovar` `{ PapelPgia }` e `POST {id}/recusar` `{ Motivo }` (obrigatório, até 500). Erros com `{Code, Message}`: `PedidoAcessoNaoEncontrado = 902` → 404, `PedidoAcessoInvalido = 903` → 400, `PedidoAcessoJaDecidido = 904` → 409, `PedidoAcessoForaDoEscopo = 905` → 403 (SGDI tentando decidir Demandas, por exemplo).
- **Aprovar = a mesma gravação da tela de gestão**: `IAcessoModuloService.PrepararLiberacaoAsync` (novo, **não grava**) deixa pronta a concessão (Demandas/PGIA, com o papel quando vier; papel só vale para o PGIA e aprovar como agente não tira papel existente) ou o `ctr_analise`; o serviço marca o pedido e grava tudo **num `SaveChanges` só**. Duas pessoas decidindo ao mesmo tempo: o token de concorrência recusa a segunda gravação inteira (nem o acesso é liberado) e ela recebe 409.
- **Encerramento automático** (pedido pendente de módulo que a pessoa passou a ter sai da fila como aprovado): `DefinirAcessosAsync` (módulos ligados na tela, com o papel), `DefinirConcessaoAsync` ao ligar ("Liberar como agente" da SGDI), `PUT governanca/pessoa/{id}/vinculo` e `POST governanca/pessoa` quando dão papel PGIA (`EncerrarPedidoPgiaAtendidoAsync` no controller), e o **`/me`** (acesso que chegou pelo Keycloak; `DecididoPor` nulo). Essas gravações toleram o pedido decidido no mesmo instante por outra pessoa (`SalvarAceitandoPedidoJaDecididoAsync`: desanexa o pedido e grava o acesso).
- **Testes**: `test-pgia/PedidoAcessoTest.cs` (35 casos: pedir, idempotência, recusas de domínio, aprovação dos três módulos, papel inválido ou fora do PGIA, conflito, concorrência com dois contextos, escopo da SGDI, quem não decide, ordem e filtros da fila, paginação saneada, os quatro encerramentos automáticos e o controller). O teste de reflexão do isolamento conhece o `PedidoAcessoController` como "autenticado". **Limitação do InMemory**: ele não tem transação, então que "nem o acesso é liberado" na corrida é garantia só do PostgreSQL (o teste confere a recusa e a situação do pedido). 554 testes no `test-pgia`.

## Modelo de papéis PGIA

`Users.PapelPgia` (nullable): `pgia_orgao` (Responsável de IA e equipe do órgão), `pgia_sgdi` (órgão central), `pgia_cgtic` (secretaria do comitê), `pgia_auditoria` (auditora externa) ou `null`. Constantes em `app/Auth/PapeisPgia.cs`. O órgão do usuário resolve-se por `Users.Unidade` → `pgia_orgao.unidade_id`. Escopo: `pgia_orgao` só o próprio órgão; `pgia_sgdi`, `pgia_cgtic` e `admin` veem tudo; `pgia_auditoria` só as auditorias designadas; usuário sem papel só registra uso de IA (art. 13). Atribuição: `PUT api/pgia/admin/papel` com `[Authorize(Roles = "admin")]` (inalterado), `PUT api/pgia/governanca/pessoa/{userId}/vinculo` (papel + unidade, SGDI/admin) ou `POST api/pgia/governanca/pessoa` (pré-cadastro por e-mail, antes do primeiro login).

**Modelo de administração (decisão do dono do produto, a própria SGDI): a SGDI pré-cadastra tudo e entrega o órgão pronto; o papel de órgão só faz as designações.** Vale para os dados do órgão (`orgao_dados`), os dados de agente público (`agente_info`) e o vínculo de acesso das pessoas (`pessoa_vinculo`) — detalhe da matriz no fim deste arquivo.

## Arquitetura e convenções

- Camadas: **Controller fino → Service (interface em `service/Interface`) → Repositório (interface em `Repositorio/Interface`) → `AppDbContext`**. Registrar tudo no `Program.cs` junto dos existentes (`AddScoped`).
- Namespaces reais não seguem as pastas à risca: `Controllers`, `service`, `service.Interface`, `Repositorio`, `Repositorio.Interface`, `Models`, `app.Models` (User/Unidade), `api.<Contexto>`. PGIA usa `Models.Pgia`, `api.Pgia`, `service.Pgia`, `Repositorio.Pgia` (interfaces em `service.Interface` / `Repositorio.Interface`).
- **JSON sai PascalCase como nas classes** (`PropertyNamingPolicy = null` no Program.cs). DTOs PGIA em `app/api/Pgia/` com propriedades PascalCase.
- Erros: `throw new ApiException(ErrorCode.X)`; códigos novos **acrescentados** ao enum `ErrorCode` (`app/api/ErrorCodes.cs`), PGIA usa a faixa 6xx. Não há middleware global de exceção.
- Paginação: `PagedRequest`/`PagedResponse<T>` (`app/api/Common/`).
- Datas puras: `DateOnly`. Timestamps: `DateTime` UTC (`DateTime.UtcNow`); conversor global `BrasiliaDateTimeConverter` cuida do JSON.
- Auditoria nas entidades de negócio: `CriadoEm`/`CriadoPor`/`AlteradoEm`/`AlteradoPor` (e-mail do usuário).
- E-mail do usuário autenticado: `User.FindFirst(ClaimTypes.Email)?.Value` (padrão do `DemandaController` em `Controllers/ProjetoController.cs` — atenção: nomes de arquivo nem sempre batem com a classe).
- Controllers: `[ApiController]`, `[Authorize]` na classe, rota `api/<contexto>` minúscula, comentários `/// <summary>` em PT-BR, permissão checada no início da action (`Unauthorized()` sem e-mail, `Forbid()` sem permissão).

## Entidades PGIA

- Em `app/Models/Pgia/`, com `ToTable("pgia_...")` e colunas snake_case via `HasColumnName` (mapeamento concentrado em `app/Models/Pgia/PgiaModelConfiguration.cs`, chamado pelo `OnModelCreating` do `AppDbContext`).
- Domínios fechados: constantes em `app/Models/Pgia/PgiaDominios.cs` + `HasCheckConstraint` reproduzindo os CHECKs do `schema_pgia_48901.sql`. Nomes explícitos de constraints/índices com prefixo `pgia` (`ck_pgia_*`, `ux_pgia_*`, `ix_pgia_*`, `fk_pgia_*`) para a revisão do script de migration.
- Adaptações do schema validado (seção 4.2 da análise): `agente_publico` **não existe** — usa-se `Users` (Guid) + extensão 1:1 `pgia_agente_info`; `orgao` → `pgia_orgao` com `unidade_id` (FK nullable para `Unidades`); FKs de pessoa são `Guid` → `Users`; **anexos habilitados (rodada de anexos): o binário vai no PRÓPRIO BANCO**, em `pgia_documento_arquivo` (bytea, 1:1 com `pgia_documento`) — a adaptação anterior "upload adiado, só metadados + nº processo SEI" **não vale mais** (o SEI continua sendo o canal oficial de tramitação); views do schema viram queries LINQ nos services. **Divergência registrada:** `pgia_sistema_ia.origem_registro` é `varchar(40)` — o schema declara `varchar(20)`, mas o próprio CHECK dele exige o valor "Instrumento vigente em revisão" (30 caracteres); o `varchar(20)` do schema é bug latente.
- Chaves: `long` identity (`bigint`) nas tabelas `pgia_*`, espelhando o schema.

### E5 · Documento do PDTIC: modelo da SGDI, cópia do órgão, prévia e PDF (2026-09-24)

  - Em `acoes_por_situacao` do RA, as concluídas entram no grupo "em dia"; no RR os grupos são pela última situação registrada, com o ciclo dela.
  - A revisão vale pela avaliação mais recente que já tem decisão (a aberta sem decisão não apaga a anterior).
  - Os blocos novos sempre em `Grupos`, também os de um grupo só (riscos e medições).
- **Limitações e o que ficou de fora:** o índice do ciclo em `pe_registro` é só `(ciclo_id)` (não `(pdtic_id, secao_id, ciclo_id)`); a unicidade de uma linha por ação (e por indicador) em cada ciclo é garantida pela grade, não pelo banco (quem grava pela rota dos registros pode incluir duas); os registros de seção por ciclo gravados antes da rodada B (sem ciclo) ficam de fora das leituras e da revisão; o carregador não acrescenta blocos a capítulo que já existe (os relatórios são modelos novos, então chegam inteiros); o RA e o RR não passam por envio nem aprovação no sistema (a aprovação do RR é registrada nos passos 7.3 e 7.4, como seção comum); o painel não tem série histórica por ciclo (só o ciclo de referência).
