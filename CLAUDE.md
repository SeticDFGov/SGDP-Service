# CLAUDE.md — SGDP-Service (API .NET 8)

API do SGDP ("API-SUBGD"), sistema em **produção** da SUBGD/GDF. .NET 8 + ASP.NET Core Web API + EF Core 8 (Npgsql/PostgreSQL) + Keycloak. O módulo PGIA (Decreto nº 48.901/2026) é implementado aqui de forma **aditiva e isolada**. Especificações na pasta pai: `analise_integracao_pgia_sgdp.md` (manda em caso de dúvida), `schema_pgia_48901.sql`, `formulario_decreto_48901.md`, `mock_formulario_pgia.html`.

## Regras invioláveis (sistema em produção)

1. **Nunca criar perfis novos nem roles novas no Keycloak.** `GetOrCreateUserAsync` (`app/Repositorio/AuthRepositorio.cs`) sobrescreve `Users.Perfil` com a **primeira** role do token a cada login — role nova no Keycloak pode trocar silenciosamente o perfil de usuários existentes. Papéis do PGIA vivem na coluna nullable `Users.PapelPgia`, administrada por endpoint do próprio sistema. **Não modificar** `GetOrCreateUserAsync`, `app/Auth/Perfis.cs` nem `app/service/PermissionService.cs`.
2. **Nenhuma alteração em tabela existente**, exceto a coluna nullable `PapelPgia` em `Users` (fase 0). Todas as tabelas novas com prefixo `pgia_`. **Nunca editar migrations antigas.** Uma migration nova por fase. Antes de fechar a fase: `dotnet ef migrations script <anterior> <nova>` e conferir que o SQL só cria objetos `pgia_*` (mais o `ALTER TABLE "Users" ADD "PapelPgia"` na fase 0). **O CI (`.github/workflows/apply-migrations.yml`) aplica migrations automaticamente no merge para a main** — já houve migration que quebrou o banco (`app/MIGRATION_INSTRUCTIONS.md`).
3. **Não alterar contrato de endpoint existente.** Exceção permitida: campo `PapelPgia` a mais na resposta do `GET /api/Auth/me` (campo extra não quebra o front).
4. Autorização do PGIA em serviço próprio: `PgiaPermissionService` (papel + ação + recurso + filtro de dados por órgão), espelhando o desenho do `PermissionService` sem tocá-lo. Perfil `admin` do SGDP tem acesso total ao PGIA. **Todo endpoint PGIA valida permissão no backend**; checagem do front é só usabilidade.
5. Endpoints públicos **somente na fase 5**, em controller próprio com `[AllowAnonymous]` explícito, devolvendo apenas os campos do art. 24 (nunca dados pessoais); solicitações do cidadão com validação de entrada e protocolo gerado no servidor.
6. **Não tocar nos testes legados** (`test/` referencia classes que não existem mais — `Projetos`, `CategoriaRepositorio` etc.; o projeto `test/` **não compila**, problema conhecido, fora de escopo). Testes novos do PGIA vivem no projeto separado `test-pgia/` (rodar com `dotnet test test-pgia/test-pgia.csproj`).
7. **Sem dependências novas** salvo estritamente necessário e justificado. QuestPDF já existe para PDFs.

## Modelo de papéis PGIA

`Users.PapelPgia` (nullable): `pgia_orgao` (Responsável de IA e equipe do órgão), `pgia_sgdi` (órgão central), `pgia_cgtic` (secretaria do comitê), `pgia_auditoria` (auditora externa) ou `null`. Constantes em `app/Auth/PapeisPgia.cs`. O órgão do usuário resolve-se por `Users.Unidade` → `pgia_orgao.unidade_id`. Escopo: `pgia_orgao` só o próprio órgão; `pgia_sgdi`, `pgia_cgtic` e `admin` veem tudo; `pgia_auditoria` só as auditorias designadas; usuário sem papel só registra uso de IA (art. 13). Atribuição: `PUT api/pgia/admin/papel` com `[Authorize(Roles = "admin")]`.

## Arquitetura e convenções

- Camadas: **Controller fino → Service (interface em `service/Interface`) → Repositório (interface em `Repositorio/Interface`) → `AppDbContext`**. Registrar tudo no `Program.cs` junto dos existentes (`AddScoped`).
- Namespaces reais não seguem as pastas à risca: `Controllers`, `service`, `service.Interface`, `Repositorio`, `Repositorio.Interface`, `Models`, `app.Models` (User/Unidade), `api.<Contexto>`. PGIA usa `Models.Pgia`, `api.Pgia`, `service.Pgia`, `Repositorio.Pgia` (interfaces em `service.Interface` / `Repositorio.Interface`).
- **JSON sai PascalCase como nas classes** (`PropertyNamingPolicy = null` no Program.cs). DTOs PGIA em `app/api/Pgia/` com propriedades PascalCase.
- Erros: `throw new ApiException(ErrorCode.X)`; códigos novos **acrescentados** ao enum `ErrorCode` (`app/api/ErrorCodes.cs`), PGIA usa a faixa 6xx. Não há middleware global de exceção.
- Paginação: `PagedRequest`/`PagedResponse<T>` (`app/api/Common/`).
- Datas puras: `DateOnly`. Timestamps: `DateTime` UTC (`DateTime.UtcNow`); conversor global `BrasiliaDateTimeConverter` cuida do JSON.
- Auditoria nas entidades de negócio: `CriadoEm`/`CriadoPor`/`AlteradoEm`/`AlteradoPor` (e-mail do usuário).
- E-mail do usuário autenticado: `User.FindFirst(ClaimTypes.Email)?.Value` (padrão do `DemandaController` em `Controllers/ProjetoController.cs` — atenção: nomes de arquivo nem sempre batem com a classe).
- Controllers: `[ApiController]`, `[Authorize]` na classe, rota `api/<contexto>` minúscula, comentários `/// <summary>` em PT-BR, permissão checada no início da action (`Unauthorized()` sem e-mail, `Forbid()` sem permissão).

## Entidades PGIA

- Em `app/Models/Pgia/`, com `ToTable("pgia_...")` e colunas snake_case via `HasColumnName` (mapeamento concentrado em `app/Models/Pgia/PgiaModelConfiguration.cs`, chamado pelo `OnModelCreating` do `AppDbContext`).
- Domínios fechados: constantes em `app/Models/Pgia/PgiaDominios.cs` + `HasCheckConstraint` reproduzindo os CHECKs do `schema_pgia_48901.sql`. Nomes explícitos de constraints/índices com prefixo `pgia` (`ck_pgia_*`, `ux_pgia_*`, `ix_pgia_*`, `fk_pgia_*`) para a revisão do script de migration.
- Adaptações do schema validado (seção 4.2 da análise): `agente_publico` **não existe** — usa-se `Users` (Guid) + extensão 1:1 `pgia_agente_info`; `orgao` → `pgia_orgao` com `unidade_id` (FK nullable para `Unidades`); FKs de pessoa são `Guid` → `Users`; upload de arquivo adiado (só metadados + nº processo SEI); views do schema viram queries LINQ nos services. **Divergência registrada:** `pgia_sistema_ia.origem_registro` é `varchar(40)` — o schema declara `varchar(20)`, mas o próprio CHECK dele exige o valor "Instrumento vigente em revisão" (30 caracteres); o `varchar(20)` do schema é bug latente.
- Chaves: `long` identity (`bigint`) nas tabelas `pgia_*`, espelhando o schema.

## Build, testes e migrations

- SDK .NET 8 instalado em escopo de usuário: `$env:USERPROFILE\.dotnet` (adicionar ao PATH da sessão se `dotnet` não for encontrado).
- Build: `dotnet build` em `app/` (baseline: 0 erros, 22 warnings pré-existentes — não introduzir warnings novos).
- Testes PGIA: `dotnet test test-pgia/test-pgia.csproj` (xUnit + EF InMemory). O projeto legado `test/` não compila — não incluir no build nem tentar consertar.
- Migrations: `dotnet ef migrations add <Nome>` em `app/` (namespace `demanda_service.Migrations`). Última migration pré-PGIA: `20260526120000_ChangeDatesToDateOnly`. Gerar e revisar o script antes de dar a fase por encerrada.
- O deploy (Dockerfile.prod) compila apenas `app/demanda_service.csproj`; projetos de teste não afetam o CI.
